# ETL результатов CRM-эксперимента

Решение от 28 октября 2026 года. Самостоятельный проект: `D:/projects/pets/data-pipeline`. Связан с A/B-кейсом общим открытым датасетом Hillstrom; код и данные других проектов не меняются. Все решения и последующие уточнения сохраняются в Markdown.

## Задача

Ежедневно получать из исходной PostgreSQL снимок результатов эксперимента, обрабатывать его настоящим Spark и публиковать согласованные таблицы в отдельной PostgreSQL для аналитики. Airflow управляет запуском, зависимостями, повторными попытками и проверками. Последний шаг формирует таблицы, графики и HTML/Markdown-отчёт.

Источник содержит итоговые показатели за 14 дней, но не даты отдельных покупок. `snapshot_date` — дата аналитического снимка, а не покупки. Исторические траты не выдаются за сегодняшние транзакции; серия снимков одного архива не является динамикой бизнеса.

## Архитектура

`CSV (только инициализация) → PostgreSQL source → Spark JDBC / Spark SQL → staging PostgreSQL warehouse → транзакционная публикация → проверка витрин → отчёт`.

В Docker работают три сервиса: исходная PostgreSQL, целевая PostgreSQL и Airflow standalone с локальным Spark. Для 64 тысяч покупателей достаточно `local[2]`; это настоящий движок Spark на одном компьютере, а не демонстрация распределённого кластера. Kafka, Hadoop и отдельный BI-сервер в первую версию не входят.

Airflow: TaskFlow API, DAG `crm_daily_etl`, ежедневный запуск в 10:00 Asia/Tomsk, `catchup=False`, `max_active_runs=1`, одна повторная попытка. Через XCom передаются только небольшие метаданные, не покупательские таблицы. Снимок фиксирует верхний `ingest_id`, поэтому новые добавления после extract не меняют состав уже запущенной обработки.

## Данные и преобразования

Оригинальный CSV и SHA-256 копируются из предыдущего проекта с указанием автора. В PostgreSQL он загружается как сырые строковые поля с техническим ID покупателя и ID поступления. Реального user_id в архиве нет: ID — номер строки фиксированного исходного снимка.

Для проверки качества добавляются ровно пять помеченных учебных дублей и семь помеченных некорректных строк. Это специально созданные дефекты; они не приписываются оригинальному источнику. Совпадение признаков разных исходных строк не считается дублем покупателя.

Spark выполняет типизацию с безопасным приведением, проверку обязательных полей и допустимых значений, карантин некорректных строк, выбор последней корректной версии по техническому ID, построение фактов и агрегатов. Нулевые траты сохраняются. Выручка хранится как decimal, не float. Крупные реальные покупки не удаляются.

## Публикация

- `customer_facts`: один покупатель на дату снимка; ключ `(snapshot_date, customer_id)`.
- `experiment_metrics`: численность, покупки, выручка, конверсия и выручка на назначенного участника по исходной группе.
- `channel_metrics`: те же показатели по группе и каналу покупок ДО эксперимента; канал не выдаётся за канал привлечения.
- `quarantine`: исходные некорректные строки и причины отбраковки.
- `etl_runs`: параметры источника, счётчики, SHA-256, время выполнения и идентификатор запуска.

Spark пишет в уникальные staging-таблицы. Их проверенные данные заменяют только указанную дату в одной транзакции PostgreSQL. Проверки целостности выполняются до COMMIT; при ошибке остаётся предыдущая согласованная версия. Повтор одного снимка не увеличивает число покупателей и сумму выручки. Другие даты не перезаписываются. Аудит хранит отдельные попытки.

Это полный ежедневный снимок малого источника, не CDC и не инкрементальная загрузка. Повторяемость и атомарная публикация проверяются запуском дважды и контролируемой ошибкой до COMMIT.

## Готовность

Нужно действительно собрать контейнер, загрузить исходную базу, выполнить Spark-преобразования и DAG Airflow, проверить повторный запуск и rollback, сформировать и визуально проверить отчёт. Отдельно фиксируются реальные проверки и ограничения; наличие одного DAG-файла не считается подтверждением автоматизации.

Все порты публикуются только на localhost. Airflow standalone и простой локальный вход используются для учебного окружения. Данные баз и метаданные Airflow живут в отдельных named volumes проекта; исходные приложения и их тома не затрагиваются. Повторный запуск не удаляет тома.

## Уточнение по окружению

Первая сборка Airflow/Spark остановилась при заполнении C: (около 40 МБ свободного места); файловая система Docker перешла в read-only. Пайплайн на этом этапе не считается проверенным. Пользователь выбрал перенос общего хранилища Docker на D: и указал `D:/projects/docker`. Подготовлены инвентаризация и копирование остановленного data disk с проверкой SHA-256. Перенос выполняется с сохранением существующих образов, контейнеров и томов; их удаление и factory reset не используются. Принятый способ — перенаправление прежней директории data disk NTFS-ссылкой на новый каталог; исходный VHD сохраняется до проверки работы Docker и затем архивируется на D:.

Уточнение после переноса: активный диск Docker находится в `D:/projects/docker/disk`, резервный исходный снимок — в `D:/projects/docker/backups/before-pipeline-20261028`. Контрольные суммы и прежняя инвентаризация проверены; Docker снова доступен для записи. Подробности миграции сохранены в `D:/projects/docker/MIGRATION.md`. Эта запись заменяет только прежний статус ожидания переноса; полный ETL ещё проходит проверку.

## Подтверждённое выполнение

Эта запись заменяет прежние статусы ожидания сборки и проверки. Собран и запущен контейнер: Airflow 3.3.2, Spark 4.2.0, Python 3.12.14, Java 17.0.21, psycopg 3.3.2. Источник и хранилище — два отдельных PostgreSQL-сервиса.

Фактический прогон: 64 012 сырых строк → 64 000 покупательских фактов, 5 учебных дублей, 7 строк карантина. Ни одна оригинальная строка не отклонена. Сумма выручки 67 258.13 USD, 578 покупателей совершили покупку. Это число покупателей с покупкой, а не число транзакций: отдельных заказов в исходнике нет. Сверены три групповых и девять канальных агрегатов с оригинальным CSV.

Пройдены 9 проверок Spark и контракта DAG. Отпечатки всех четырёх аналитических таблиц совпали после повторного прогона. Контролируемая ошибка внутри транзакции до COMMIT сохранила прежние отпечатки и записана в аудит как failed. Тестовая ошибка является намеренной проверкой отката, не неустранённой неисправностью.

Airflow самостоятельно выполнил scheduled-запуск `scheduled__2026-10-28T03:00:00+00:00`, затем ручной проверочный запуск `portfolio_check_13aa4ad4eb9c`; оба завершились success, все четыре задачи ручного запуска success. Ежедневное расписание 10:00 Asia/Tomsk включено. Сформированы CSV, PNG, HTML и Markdown-отчёт; графики проверены визуально.
